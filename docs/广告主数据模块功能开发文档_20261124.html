一、需求定位与隔离边界

定位：这是一个全新一级功能模块——新增一级菜单入口，界面布局与结构完全按本需求独立设计；不改动任何现有功能模块的菜单、界面布局与功能实现。现有模块（素材工作坊、创意工作台、素材创意模板库、素材标准库、提示词管理、素材历史、系统设置等）保持原样，新旧之间仅共享登录态与基础组件样式变量。

设计目的：把「某个渠道的接口怎么调」沉淀成标准模板，把「本次用哪个账号调」变成实例配置，把「拉回来的数据怎么存」统一成一套字段。以后接入新的联盟 / 广告主 API，只需新增一份模板与映射，不改业务代码、不改表结构、不改报表。CJ 是第一个落地模板。

关于凭据：对话中提供的 API Token 与登录密码均未写入任何文件。正式实现中，Token 由界面密码框输入、加密存储、列表脱敏、不回显、不写日志、不下发前端；建议正式配置前在 CJ 后台作废旧令牌、重签并通过环境变量注入。
隔离保证：新增独立路由与页面组件；现有页面的 Tab 枚举、菜单分组、布局与交互代码不做任何修改；新增数据表独立命名，通过 ensure_schema() 增量建表，不影响现有表结构。

3.2 接口关键约束（来自 CJ 官方文档）

  • 端点 POST https://commissions.api.cj.com/query，GraphQL 只读；认证用 Authorization: Bearer <个人访问令牌>，开发者 Key 已弃用。
  • 我们是发布者，用 publisherCommissions 查询；forPublishers 参数是发布者公司 ID（CID），不是登录邮箱——拿不到 CID 无法发出第一条有效请求。
  • 对象层级（V4.129 澄清）：HTTP 端点只有一个 POST .../query；GraphQL 查询字段是 publisherCommissions，返回 PublisherCommissions! 包装对象；明细在 records: [PublisherCommission!]! 中。不存在名为 PublisherCommission 的独立接口，代码与界面写「请求 PublisherCommission」指的是读取 records 里的明细对象。
  • 日期口径统一用 sinceEventDate / beforeEventDate（UTC ISO 8601）；官方也支持 postingDate / lockingDate 边界，但本系统按定稿以事件日期为准。
  • 三条硬限制：日期跨度 ≤31 天、单次 ≤10,000 条、200 次/5 分钟。V4.131 调整：本系统「测试」窗口默认近 7 天（CJ 佣金明细通常延迟 1–3 天，固定 1 天窗口常返回空 records），可在测试抽屉内调整起止日期，仍须满足 ≤31 天。
  • situations 字段解析较慢，首版不取。

四、定期请求任务规划

任务项规划
任务绑定一个任务绑定一个 API 连接实例；一个实例可建多个任务（如"日报"与"历史回填"）。
调度方式复用现有 model_health 的 startup 后台协程模式，新增佣金拉取协程；启停对称，不引入新调度框架。
触发频率默认每日一次（可配置为每 6 小时）。任务配置含：频率、回溯窗口（默认 7 天）、首次回填天数（默认 90 天）。
执行流程按模板窗口切片 → 游标翻页 → 限流等待 → 原始落库（幂等 upsert）→ 重算事实表 → 写运行记录。
水位管理按 eventDate 重叠窗口拉取（7 天回溯，避免漏掉迟到修正）；水位与游标写入 SystemState / 运行记录，重启后可续跑。
失败处理认证失败 / count=0 / 字段异常 / 超限分别给出明确错误；指数退避重试；失败不静默，运行记录可见并可手动补拉。
可观测每次运行记录：起止时间、窗口、拉取条数、游标位置、状态、错误；界面「运行记录」区可查，支持"获取难点排查"。
V4.134 已落地：调度复用 api_fetch_task / api_fetch_run 与 model_health 的 startup 协程模式，不新增调度框架；按连接配置执行，SystemState 水位 + 抢占锁去重，重启不重复跑。历史回填按 30 天步长 + 1 天重叠切片，单片跨度始终 ≤31 天；每片走同一条游标翻页与幂等落库链路，结束后跨批次重算取消单。api_fetch_run.run_mode 区分 manual / scheduled / backfill。全局开关 ADVERTISER_FETCH_ENABLED=0 停调度，ADVERTISER_FETCH_AUTO_BACKFILL=0 关闭首次自动回填，回滚不删数据。

4.1 任务执行子步骤（模板驱动）

  1. 读取实例配置（Token / CID / Endpoint）与模板规则，校验必填项完整。
  2. 确定窗口：当日任务 = 最近 7 天；回填任务 = 从起始日按 ≤31 天分片。
  3. 用模板查询骨架发起请求，带 sinceEventDate / beforeEventDate / forPublishers，显式读取 records 中的 PublisherCommission 明细。
  4. 解析响应，按 api_field_map 写入原始层与事实层，commissionId 幂等去重。
  5. 若 payloadComplete=false，取 maxCommissionId 作游标继续；否则进入下一窗口。
  6. 全窗口完成后重算事实层（合并修正、标记取消单），更新水位与运行记录。

6.1.1 字段冲突消解规则（V3.1 定稿 · 所有模板通用）

用户定稿原则：新增字段必须先与统一表中已存在的列逐项比对；凡与已有字段冲突的，对应字段不新增，改为复用已有列（或仅调整其可见性）；只新增确认无冲突的字段。禁止为同一语义建立两个物理列。

同名同义：上游字段已有对应业务列commissionId → 已有 commission_id（第 1 项 ID）不新增列、不新增映射行；沿用原有列与原展示名配置，仅在口径说明中标注对应关系

异名疑似同义：名称不同但语义可能重叠如后续模板出现 campaignName 与已确认的 campaign_name ← advertiserName先确认口径，不自动建列；确认同义则复用已有列，确认不同义才允许新增，并在映射表写明两者区分
无冲突：统一表中不存在对应列aid / clickDate / country / coupon / publisherId / publisherName才允许 ADD COLUMN 新建可空列并新增映射行与展示名配置
执行红线：① 建表前先输出"新增字段冲突比对表"，逐项标注复用 / 提升可见 / 新增；② 不得靠修改展示名来规避物理列冲突；③ 冲突字段的历史数据不迁移、不覆盖，复用已有列即可；④ 只有判定为"无冲突"的字段计入迁移脚本的新增列。

单价 unit_price_usd

qty_internal = Σ items[].quantity（简单销售为 1），仅作计算中间量。

主表均价 = sale_amount_usd / qty_internal；子表存每项 perItemSaleAmountUsd 精确值。

取消单 is_void

按 (orderId, originalActionId) 合并全部原始+修正明细。

net_commission==0 且 net_sale==0 → true；另识别 CJ 取消机制的"零额记录 + 全零冲正记录成对出现"→ true。

不使用 actionStatus=REVERSED（CJ 官方枚举无此值，见 6.2.1）；修正在正单之后到达时，每次拉取后重算并回填该订单所有明细行。

七、可维护性保障：三条硬性设计约束

上线后仍需持续纠正三类内容——展示字段名、字段映射、数据库列名。三条保障缺一不可，列为开发任务硬性验收项。

保障一 · 展示名配置层 api_field_label

报表中文展示名不得硬编码在前端。表含 scope / column_key / label / unit / format / sort_no / visible；表头、顺序、单位、格式全部由该表驱动。改名 = 改配置行，零迁移、零发版。

验收：全局无硬编码字段中文展示名；改一行配置刷新后表头即变。

保障二 · replay 重放工具

POST /advertiser-data/replay?template_id=...&connection_id=...&dry_run=true&limit=... advertiser_ingest.replay_mapping(...) ① 读 api_source_record.payload_json ② 用当前 api_field_map 重新映射 ③ 按 (template_id, external_id) upsert 回 api_unified_fact ④ 触发订单净额 / is_void 回填

V4.132 已实现。改映射后从原始 JSON 重放历史；幂等、支持 dry_run=true 只预览覆盖告警而不写库（接口默认 dry_run）。api_field_map 已含 version/effective_from 字段，按版本回放留待后续按需启用。

验收：专项验证 dry_run 不写库、apply 重放幂等（第二次全部 unchanged）、覆盖告警可预览。

保障三 · 版本化列迁移

结构变更写 backend/migrations.py 版本函数 + ensure_schema()，版本号记入 schema_migrations；SQLite 用 ALTER TABLE ... RENAME COLUMN。rename_column(old,new) 助手一次同步四处：api_field_map.target_field → 合并视图 → 写入代码 → 报表查询。迁移前备份 + 回滚说明 + 一致性校验。

验收：迁移可重复执行不报错且有版本记录；改列名后映射表/视图/报表三处一致；回滚可执行。
优先级：只是"叫法不顺"时优先用保障一改展示名，不动物理列名；仅语义确需变更时才用保障三。

V3.1 新增字段对三条保障的处理约定

保障本次新增字段的落地动作
一 · 展示名配置层为 8 个新增业务字段（ad_id/click_date/correction_reason/country/coupon/posting_date/publisher_id/publisher_name）各写一行 api_field_label；可空字段展示为空白而非 "null"；枚举字段配中文值映射。第 1 项 commission_id 沿用现有行，不重复登记。
二 · replay 重放8 个字段的上游值本来就在 api_source_record.payload_json 里（原始层零丢失），因此新列上线后无需重新调用 CJ API：跑一次 replay_mapping() 即可回填历史；dry_run 可预览 20 字段的新旧差异。
三 · 版本化列迁移6 个全新建列用 ALTER TABLE ADD COLUMN（可空、无默认值）；2 个已有列（correction_reason/posting_date）不改列名、不迁数据，仅把 api_field_label.visible 从隐藏改为可见——这正是"改展示优先于改物理列"的范例。迁移版本号记入 schema_migrations。
验收补充：20 个业务字段全部有展示名配置；新列在空库与已有历史库两种场景均可建；历史库 replay 后 8 个新字段有值（CJ 确实返回的记录）且原记录不被覆盖。
