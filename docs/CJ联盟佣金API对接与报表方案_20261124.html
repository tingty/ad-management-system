〇、先行结论与安全处理

结论：CJ 提供的是佣金明细明细流（GraphQL），不是现成报表接口。方案为：用个人访问令牌按 publisherCommissions 增量拉取 → 原始落库 → 合并修正记录形成事实表 → 本地聚合出报表。技术上可行，且能复用现有系统的调度、SystemState 与前端框架。
安全提醒（请立即处理）：你在本对话中明文提供了登录密码和 API Token。
1) 建议马上在 CJ 后台重新生成一枚个人访问令牌，并作废旧令牌——对话记录不等于安全渠道。
2) 本方案未把任何凭据写入文件；正式实现中令牌只通过环境变量 CJ_API_TOKEN 注入后端，不入库、不进 git、不下发前端、不打印日志。
3) 登录密码在本对接中完全用不到——API 只认 Bearer Token。
首要阻断项：API 的 forPublishers 参数要的是发布者公司 ID（CID），不是登录邮箱。你给的 partners@cocomob.com 是登录账号，需先在 CJ 后台查到对应 CID 才能发出第一条有效请求。这是开发前必须拿到的输入。

二、四个必须先说清的边界

1 · CID 缺失

API 不认邮箱。必须先从 CJ 后台拿到发布者 CID，否则请求恒返回 count=0 或认证/参数错误。

2 · 没有花费数据

CJ 只回传收入侧（销售额、佣金），不含广告花费、曝光、点击。因此真正的 ROI / ROAS / CTR / CVR 单靠此 API 算不出。

3 · 修正会回改历史

订单可能在数天后被取消或调整。只拉「昨日新增」会漏掉修正，必须按 postingDate 回溯重叠窗口。

4 · 素材归因需预埋

佣金天然带 aid（CJ 广告 ID）与网站维度；要归因到「我们自己的素材编号」，需在 CJ 追踪链接里提前埋标识并验证能否从 source / verticalAttributes 回读。

因此第一版报表的定位：做「佣金收入视角」——总佣金、销售额、订单数、佣金率、AOV、按广告主 / 网站 / 广告 / 国家 / 时间的分布与趋势。投入产出（ROI）先预留字段与接口，等广告平台花费数据接入后再补，不编造分母。

定期拉取策略

  • 增量水位：按 postingDate 拉「最近 7 天」重叠窗口（可配），覆盖修正延迟；每天定时一次，重跑幂等。
  • 历史回填：首次按 ≤31 天分段回溯（如 90 天 = 3 段），逐段游标翻页。
  • 限流：串行请求、批次间限速（保守 ≥1.5 秒/次），远低于 200/5min 上限；失败按指数退避重试。
  • 失败可见：每次运行写 cj_sync_run；认证失败、count=0、字段异常分别给出明确错误，不静默空跑。
