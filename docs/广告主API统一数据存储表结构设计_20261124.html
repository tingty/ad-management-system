一、读取对象与数据粒度

CJ publisherCommissions（GraphQL，只读）返回的核心对象是 PublisherCommission。关键事实：

  • 一条 = 一个订单的一笔佣金事件：以 commissionId 唯一标识，携带 orderId（广告主订单号）、金额、状态、商品明细 items[]。
  • 一个订单可能有多条：原始单 original=true 与其后所有修正单 original=false 共用同一个 orderId、不同 commissionId；修正记录是增量（delta），必须合并才是订单最终金额。
  • 游标分页：maxCommissionId → sinceCommissionId，直到 payloadComplete=true；窗口 ≤31 天、单次 ≤10,000 条、200 次/5 分钟。
粒度决策：统一事实表以一条 publisherCommission = 一行（明细粒度），保证与 API 一一映射、修正记录零丢失；"订单最终金额 / 是否取消单"通过合并视图按 (orderId, originalActionId) 聚合得出。

CJ 官方给出的修正 / 取消示例

// 同一 orderId=69461063 的两条明细，合并后净额为 0 → 取消单 { "original": true, "pubCommissionAmountUsd": "1.852", "saleAmountUsd": "61.742", "orderId": "69461063" } { "original": false, "pubCommissionAmountUsd": "-1.852", "saleAmountUsd": "-61.742", "orderId": "69461063" }

简单销售直接把金额相加；高级销售（含 item）按 SKU 合并数量后再乘单价与单项佣金。只取"最新一条"或只看"原始单"都会算错。

五、派生字段的计算规则

5.1 单价（unit_price_usd）

  1. 中间量：qty_internal = Σ items[].quantity（高级销售）；简单销售无 item 明细时 qty_internal = 1。该值不落为统一表字段，仅用于计算。
  2. 主表均价：unit_price_usd = sale_amount_usd / qty_internal（qty_internal = 0 时为 0）。
  3. 子表精确值：每项存 items[].perItemSaleAmountUsd，多 SKU 时以子表为准。
  4. 修正记录： quantity 为增量（可为负），均价按该条明细自身的金额与数量计算；订单最终单价以合并视图的净额为准。

5.2 合并后是否为取消单（is_void）—— 关键规则

按 (template_id, order_id, original_action_id) 分组，把该订单的全部明细（原始 + 所有修正）合并后才判定：
net_commission = SUM(commission_amount_usd) -- 原始 + 各修正增量 net_sale = SUM(sale_amount_usd) is_void = (net_commission == 0 AND net_sale == 0)
  • 完全取消：正负增量相抵，净佣金与净销售均为 0 → is_void=true（对应官方示例）。
  • 不再使用 REVERSED：CJ 官方 ActionStatus 只有 closed / extended / locked / new；视图与回填统一按净额归零判定，与 v_api_order_final 实现一致（V4.130 纠正）。
  • 部分修正未归零：净额 ≠0 → is_void=false，报表按净额显示最终金额，而非原始单金额。
  • 回填机制：修正单可能晚于原始单到达。因此 is_void 由每次拉取后的合并任务重算并回填到该订单所有明细行，保证历史行同步更新。
订单最终视图 v_api_order_final：按订单聚合输出"最终销售 / 最终佣金 / is_void"，报表默认查这个视图看订单结果，需要追明细时下钻到 api_unified_fact → 原始 JSON。

六、写入与合并流程

  1. 拉取：按模板规则（Bearer Token + CID + Endpoint），游标分页拉全，7 天重叠窗口回溯迟到修正。
  2. 原始留痕：每条 commission 原样 JSON 入库，哈希检测内容变化（修正会变）。
  3. 映射：读 CJ 模板的 api_field_map，分发到 12 业务列 / 技术列 / item 子表 / ext；做覆盖检查。
  4. 事实入库：按 (template_id, external_id) upsert，同一 commission 重复拉取只更新。
  5. 合并回填：按订单重算净额与 is_void，回填到该订单所有明细行。
  6. 报表：订单视图查最终口径，明细视图查原始逐笔，全程不需要知道来自哪个模板。

九、可维护性保障：三条硬性设计约束

上线后仍需持续纠正三类内容——展示字段名、映射关系、数据库列名。为使这三类修改都能低成本完成且不留遗漏，开发时必须落实以下三条保障，缺一不可，均列入第十节开发任务清单并作为验收项。

保障一 · 展示名配置层（展示名与物理列解耦）

目的：报表中文展示名不得硬编码在前端组件里。改名 = 改配置行，零数据迁移、零停机、无需重新发版。

字段类型说明
idInteger PK自增
scopeString作用范围：global 或某 template_id（渠道可覆盖全局展示名）
column_keyString对应物理列名 / 视图列名，如 commission_amount_usd
labelString展示名，如"佣金金额"；改这里即改报表表头
unit / formatString单位（USD/无）与格式（金额两位小数、日期 YYYY-MM-DD）
sort_no / visibleInteger / Boolean列顺序、是否展示，可独立调整
  • 报表表头、字段顺序、单位、格式化全部由这张表驱动，前端渲染时不写死任何中文字段名。
  • 新增/隐藏列、改展示名 → 只改配置行，不动数据库、不动数据、不发版。
验收：报表所有表头均来自 api_field_label；代码全局搜索不到硬编码的字段中文展示名；改一行配置后刷新页面表头即变。

保障二 · replay 工具（映射变更可重放历史）

目的：改了 api_field_map 映射后，历史数据仍按旧映射落库。必须从原始 JSON 重放，才能把新映射同步到历史。

replay_mapping(template_id, since, until, order_ids=None, dry_run=True) # 预览差异 ① 读 api_source_record.payload_json（未映射的原始记录） ② 用当前（或指定版本）api_field_map 重新映射 ③ 按 (template_id, external_id) upsert 回 api_unified_fact ④ 触发订单合并回填（净额 / is_void）
  • 依赖原始层零丢失的原样 JSON——这是能保证"改了映射不丢历史"的根本前提。
  • 必须幂等、可断点续跑；支持 dry_run 预览将变更哪些行、变更前后值。
  • 映射表增 version / effective_from 字段（可选但推荐），支持按映射版本回放与审计。
  • 触发时机：映射变更保存后提示"是否重放历史"，或管理端手动执行；口径变更（如日期、单价、取消单规则）后必须执行。
验收：改完映射后 replay 一次，历史报表数值与预期一致；dry_run=true 能列出变更行且不写库；重复执行结果一致（幂等）。

保障三 · 版本化列迁移（表结构变更可追溯、可重复）

目的：数据库列名/类型变更不得手工临时执行，必须走版本化迁移脚本，避免遗漏引用、无法重复、无版本记录。

  • 所有结构变更（加列、改列名、改类型）写入 backend/migrations.py 的版本化迁移函数，由 ensure_schema() 统一执行。
  • 用 ALTER TABLE ... RENAME COLUMN 改列名（SQLite 3.25+），并把迁移版本号记录到 schema_migrations 表，防止重复执行。
  • 提供一个 rename_column(old, new) 助手，一次性串联四处同步修改：api_field_map.target_field → 合并视图 v_api_order_final → 写入代码 → 报表查询。避免只改一处导致其他处引用旧列名。
  • 迁移前自动备份 DB；保留回滚说明；升级后跑字段一致性校验（映射表/视图/报表三处列名一致）。
验收：迁移可重复执行不报错且有版本记录；改列名后映射表、视图、报表三处一致；回滚方案可执行。
优先级建议：只是"叫法不顺"时，优先用保障一改展示名，不要动物理列名。物理列名保持稳定，仅在语义确需变更时才用保障三。
