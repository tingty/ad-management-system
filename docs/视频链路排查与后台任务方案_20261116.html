一、结论先说

文档的核心判断是对的：线上显示「连通测试成功」与「出不了片」可以同时成立，因为当前测试只证明端点回了一个 2xx，并不证明拿到了任务号、更不证明成片可下载可播放。我在代码里逐条核实了 F01–F08，八项全部成立，其中三项构成这次失败的直接嫌疑，另有两项是"看起来成功、其实是假象"的元凶。

① 不是"没配视频模型"V4.78 已修复选型（#16 / wan3.0-video 确实被选中）。问题发生在"提交之后的取片与判定"。
② 失败被折叠成"成功"轮询异常、查询 4xx、无成片字段，全部静默吞掉 → 回退分镜 → 后台任务仍写 done。用户只看到"完成但没有视频"。
③ 成片可能根本不是视频媒体解析会递归接受任意 http 字符串；已复现：PENDING 响应里的输入图片 URL 被当成成片，直接存成 .mp4。
④ 后台任务名不副实任务只在单进程内存里、无归属校验、刷新即中断、不能并行。要做成"能离开页面"，必须持久化。
必须先纠正的表述口径："连通测试成功 / 配置齐全"只能推出「提交被受理」，不能推出「可出片」。诊断与设置页现有文案（含我在 V4.78 写的"可直接生成"）都要降级为四态：配置完整 → 提交受理 → 查询可用 → 出片验证，只有最后一态才允许说"能出片"。
对后台任务的态度（提前说）：需求成立，但文档给的界面复杂度偏高（筛选 + 搜索 + 三种重试 + 子任务 + 预览下载堆在一个抽屉里）。我的建议是后端做重（持久化、状态机、恢复），前端做轻（两个入口 + 一行一状态 + 一个可执行按钮）。详见第四节。

这三条最像本次线上失败的原因

  1. F02 + F03：厂商任务其实在跑，但轮询某几轮拿到 4xx/网络抖动被 continue 掉；120 轮耗尽或提前退出后回退分镜，后台任务照样标 done → 用户看到"完成 + 空视频"。
  2. F04：图生视频时提交响应里带 input.image，被当成同步成片下载 → 得到一个 PNG 改名的 .mp4，前端 <video> 黑屏。与"有产物但播不了"的现象高度吻合。
  3. F05：即使下载到了真正的成片 URL，签名 URL 过期 / 302 / HTML 错误页都会落成坏文件，且没有任何校验拦截。
仍缺的关键证据（文档也说对了）：本次失败请求的 provider request_id / task_id、每次查询原文、下载响应头。补齐这些之前不宣称"唯一根因"。修复顺序应当是先把这些证据记录下来，而不是先改逻辑——否则改完仍无法证明修好了。

三、修复方案

原则：分镜永远不等于视频；未证实的结果不写成功；不重复提交收费任务；每一步都留可脱敏取证的痕。

3.1 状态机（唯一事实）

queued 排队→ submitting 提交中→ provider_pending 模型生成中→ downloading 下载中→ validating 校验中→ succeeded 成功
failed（终态，可重试） needs_attention 待核实（非终态，可继续查询） canceled / stopped（用户主动）

succeeded 的四个必要条件（缺一不可）：① 供应商返回成功态；② 媒体下载 200 且落到临时文件；③ 媒体探测通过（存在视频流 / 可解析 / 时长与宽高非零）；④ 资产已入库且与任务关联。分镜脚本、外部临时链接、videos=[] 都不满足。

3.2 错误码与处置（决定前端只显示"一个可执行按钮"）

error_code触发场景子任务状态用户看到的一句话唯一可执行动作
config_missing没有可出片的视频配置failed还没配置可用的视频模型去配置
submit_rejected提交 4xx（401/403/400）failed提交被拒绝：Key / 白名单 / 参数看原文 → 修复后重试
submit_unknown提交超时或回包无任务号needs_attention提交结果待确认，正在核实继续核实（禁止自动重提）
poll_auth查询 401/403needs_attention任务已提交，但查询鉴权失败修复 Key 后继续查询
poll_rate_limited429running（退避）厂商限流，已自动退避无需操作
poll_timeout超过业务期限仍在生成needs_attention生成时间偏长，仍可继续取回继续查询
provider_failed厂商返回 failed / 内容审核failed模型生成失败：{厂商原因}重新生成
no_media_field成功态但无约定媒体字段needs_attention厂商已成功但未取到成片地址继续查询 / 联系支持

3.3 解析：按协议族显式映射，禁止递归兜底

把 _video_find_media 从"主路径"降级为"仅同步直出协议的最后手段"，并引入两个显式解析器：

协议族提交响应取查询响应取媒体字段（白名单）
dashscope_maasoutput.task_id / output.task_status同上 + output.code/messageoutput.video_url → output.results[].url
generic-video 网关id / task_id / job_idstatus / stateoutput.url / result.url / results[].url / data[].url
kelingdata.task_iddata.task_statusdata.task_result.videos[].url
  • 提交阶段先取任务号；只有显式声明 body_shape=sync 的配置才允许在提交响应里取媒体。
  • 规则：有 task_id 且状态非终态 → 绝不解析媒体；无 task_id 且无白名单媒体 → no_media_field + 保留脱敏响应摘要（≤500 字）。
  • 未知结构一律判"不通过"，不再"尽力而为地猜"。

3.4 轮询：可配置退避 + 业务期限 + 保留任务号

响应处置是否继续持有任务
2xx + pending按退避继续（3s→6s→10s→20s，上限 30s）是
429 / 5xx / 网络异常指数退避，累计失败次数记入 attempts，连续 5 次才升 poll_network是
401 / 403立即 poll_auth，停止轮询但保留 task_id是（可恢复）
超过业务期限（默认 20 分钟，可配）转 needs_attention / poll_timeout，不判失败、不重提是（后台继续低频查询）
"6 分钟"这个数必须从代码里消失。它既不是模型的真实上限，也不是用户能理解的承诺。改为：页面上只显示"已等待 N 分 M 秒 · 模型生成中"，后台按业务期限自动续查，用户随时可以离开。

3.5 下载与校验（把"有链接"变成"能播"）

  1. 流式下载到 uploads/tmp/{asset_uuid}.part：超时 300s、上限 200MB、跟随最多 3 次跳转、记录最终 URL 与 content-type。
  2. 三层校验：
    • 响应层：2xx + content-type 不是 text/* + 长度 > 20KB；
    • 容器层（纯 Python，零依赖）：MP4 必须有 ftyp（偏移 4）与 moov；解析 mvhd 得 duration、tkhd 得宽高；WebM 检查 EBML 头；
    • 探测层（可选装 ffprobe）：拿到 codec / duration / width / height，作为实际值写库。
  3. 失败不乱丢：删临时文件、保留 provider_url 与响应头摘要，状态 failed/download_failed，操作只给"重新下载"（不重新生成）。
  4. 通过后原子落盘：os.replace() 重命名为 video_{batch8}_{asset_uuid}.mp4，入库 CreativeAsset（kind=video）。
不装 ffmpeg 也能先跑：容器层校验已经能拦住 PNG 改名、HTML 错误页、空文件、截断文件这四类最常见的假成片；ffprobe 只是把"时长/宽高"从"计划值"升级为"实测值"（A12 需要）。建议在 Dockerfile 里加 apt-get install -y --no-install-recommends ffmpeg，并以"有则用、无则降级"的方式接入。

3.6 时长与命名（F07）

  • dashscope 分支按契约补 parameters.duration；先做一次受控实测确认 wan3.0-video 接受的取值集合，不支持时不要硬塞，改为在结果里标注"模型固定时长"，并把 requested_duration 与 actual_duration 同时存下。
  • duration_sec / width / height 一律来自探测值；页面显示实测值，与所选不符时显式标注（沿用 V4.75 的"输出比例如实标注"思路）。
  • 文件名带批次与资产 UUID，彻底消除同秒覆盖。

四、后台任务功能评估（重点：可用性易用性，而不是界面复杂度）

4.1 先定义"这个功能成功的样子"

可用性（不做到就等于没做）关页面 / 刷新 / 换菜单 / 服务重启后，任务仍在、状态真实、成片能取回；不会因为等待而阻塞下一份创作。
易用性（判断标准）用户不需要学习新概念：不新增一级导航、不新增二级页面、不需要理解"批次/子任务/租约"这些词。
复杂度上限界面上新增元素 ≤ 2 个（一个按钮 + 一个入口）；抽屉里默认可见的交互 ≤ 3 类（看状态、看结果、点一个按钮）。

4.2 我的界面方案：两个入口 + 一个抽屉，不加导航

  • 顶部固定条：左侧 ＋ 新建创作（任何阶段都可点，只清空草稿、不动历史）；右侧 任务 3（数字 = 本人排队 + 进行中的批次数，为 0 时显示"任务"且弱化）。
  • 右侧抽屉（约 400px）：标题「创作任务」；默认两个分组：进行中 / 需处理；已完成默认折叠并按 7 天保留。不阻塞底层工作台，不跳页。
  • 一行 = 一个批次：产品名 · 图片/视频 · 阶段文案 · 已等待 · 2/3 成功数。点行展开子任务，不进入新页面。
  • 提交后的反馈：toast「已加入后台任务，可继续创作」+ 两个动作（查看任务 / 开始新创作）。抽屉关掉、切模块、刷新都不影响任务。
  • 完成提醒：非当前批次完成时，用现有右下角浮窗提示一次（复用 V4.77 的 CwTaskDock 位置），不再叠加新的红点体系。

4.3 我建议砍掉的复杂度（并说明理由）

文档提议建议理由
筛选（进行中/已完成/需处理）+ 按产品名或任务号搜索首版砍掉搜索只留两个分组 + 已完成折叠本人任务通常是个位数、按时间倒序即可；搜索框是"我做了很多任务"才需要的功能，先做会让人以为要管理一堆任务。
三种重试动作（重新下载 / 继续查询 / 重新生成）全列出来按 error_code 只显示一个三个按钮并排会让用户猜"我该点哪个"。错误码已经决定了唯一正确动作，界面直接给那一个。
供应商取消（若厂商支持）不做只做"停止后续步骤"并说明在途任务可能仍会完成阿里云百炼当前没有取消契约。做一个点不动的取消按钮，比没有更伤信任。
生成百分比不做四态阶段文案 + 已等待时长厂商不返回进度，百分比只能编。V4.76/V4.77 已确立"不把等待时间换算成百分比"的做法。

一次性展示批次 + 子任务 + 阶段 + 错误码 + 资产 + 操作两层折叠默认只到子任务层，错误码收进"技术详情"移动端 400px 抽屉塞不下；默认给人话，排障时再展开。

  • cwTask.ts 降级为「抽屉开关 + 当前选中批次」，不再持有任务事实；事实来自服务端列表。

五、验收矩阵落地（A01–A14 → 实现点与测法）

六、不做清单与风险

类别内容理由 / 处置
明确不做扩大超时、隐藏异常、加提示词、继续用分镜兜底冒充成功这四种"修复"会让问题更难被发现，文档也明确禁止
明确不做任务搜索、独立任务页、供应商取消、假进度百分比见 4.3，增加操作面但不增加可用性
明确不做重写图片生成引擎图片链路已稳定，只需在批次视图里聚合
风险SQLite 并发写（worker + 请求）已有 WAL + busy_timeout 30s；worker 单实例串行领取，写事务短小
风险ffmpeg 增加镜像体积可选安装 + 纯 Python 容器校验降级；不装也能拦住四类假成片
风险wan3.0-video 是否接受 duration 未知先受控实测；不支持则标注"固定时长"，不硬塞参数
风险旧内存任务无法恢复上线时若有运行中任务，明确告知需重新提交；不宣称"全部可恢复"
风险计费模拟 stub 覆盖全部故障路径；真实调用设定次数与费用上限
