二、文档值得借鉴的地方

1. 事实与判断分离
「无产品价值表达」来自可见样本与代码路径；「可能影响转化」只作为专业判断，CTR/CVR/ROAS 必须关联广告账户验证。这个边界应写进所有验收口径，避免用大模型自评分或文件生成成功冒充效果结论。
2. 先修可复现缺陷，再谈效果
不把「吸引力不足」当成一句提示词就能解决，而是先修状态漂移、证据断链、逐项错误丢失等基础设施问题——这与我的一贯判断一致。
3. 保留既有能力，最小界面改动
文档明确「无需从零开发三步流程、参考图上传、路线勾选、分镜对话」，与用户「最小改动」要求吻合。我据此拒绝了大改交互的冲动。
4. 优先级与意图分层
「平台硬规则 ＞ 已确认事实 ＞ 用户策略 ＞ AI 建议 ＞ 默认行业表达」这条优先级链很实用，可直接作为未来 creative_intent 冲突裁决的准则。
5. 验收要打在真实请求上
文档反复要求「mock 供应商实际请求能捕获唯一标记」「不只检查文件里有没有关键词」。这比我过去偏静态断言的测试更硬，值得作为后续测试改进方向。
6. 效果验证的实验设计
同产品/目标/受众/版位/落地页条件下比较概念，提前定义预算与最小可检测改善，不因 CTR 变高就认定有效——这部分属业务验证，我完整保留为待确认项。
对我自己的改进要求：后续专项测试要从「文件里有没有关键词」逐步升级到「拦截真实供应商请求、断言最终提示词与请求快照」。本次 7 项修复仍以静态断言 + 临时数据库行为测试为主，已在方案中为下一阶段留出升级路径。

五、待确认优化方案（9 类，按建议优先级排序）

以下方案都涉及产品决策、交互重构、数据契约或外部成本，我没有进入开发。每项给出「解决什么 → 建议做法 → 改动范围 → 验收 → 风险/需你拍板」。

P0 · 信任与事实 方案 A：C02 证据链入统一分析

解决：_build_cw_result 只存 snapshot，不把 evidence_index / chain / 原文 / 限定条件写入 analysis，导致证据门拿不到可定位原文，历史样本出现 evidence_status=unverified、source_id=null。

建议：以同一抓取快照为单一来源，analysis 内嵌证据索引与原文、URL、时间、claim 映射；人工文本另起独立编号；分析模型返回的卖点必须引用存在的 E 编号并保留范围条件。

改动范围：routers._build_cw_result、services 证据打包逻辑、claims.EvidenceSnapshot、schemas；新增证据落库测试。

验收：每个对外承诺可还原原文；不存在的 ID 被拒；只有 ID 无原文不得标已核验；新任务不以 legacy_unverified 冒充通过。

需拍板：是否把「无证据即阻断生成」设为硬门（会让部分历史可生成的任务转 needs_input）。

P0 · 转化核心 方案 B：C03 路线成为独立生成概念

解决：图片概念仍由文案生成，其余勾选路线混作修饰，导致「路线不同、产品主体与价值相同」，甚至共享 concept_key。

建议：每条路线独立产出结构化 CreativeConcept（受众任务、阻力、单一承诺、可见证据、产品动作、场景、下一步），concept_id 绑定 route_id + intent_version；不再混入其他候选路线；行业配置只给边界不替代策划。

改动范围：creative_config.build_concept、media_ad 图片概念构造、image_prompt_rule 的「辅助路线」策略、CreativeWorkbench 选路透传。

验收：选两条路线必须在价值切入/动作/证据上有实质差异且可追溯；跨尺寸同一概念不能只换颜色。

需拍板：是否废弃「辅助路线修饰」机制——这会改变现有「一次出图融合多路线」的产品行为。

P1 · 用户意图 方案 C：C01 意图打通 analyze + 路线卡可编辑

解决：V4.101 的 brief 已进文案/路线/图片/视频规划，但 analyze 阶段不接收用户意图，imageSupplement 仍只作用于图片视觉，路线卡只能勾选不能编辑。

建议：在现有补充框承载结构化 creative_intent（受众/目标/核心价值/场景/风格/禁止项），三类素材共用；自然语言解析为 intent_patch，返回变更摘要与冲突；改视觉项仅重编译视觉，改受众/价值则重策划概念与文案；路线卡增加「就地改一句推荐描述」。

改动范围：CWAnalyzeRequest、/cw/analyze、/cw/routes、creative_brief、前端补充框与路线卡、草稿快照。

验收：输入「面向首次装修业主，不做全息，重点看清家具布局」后，路线/视觉简报/最终请求均体现该意图，事实与授权参考不变。

需拍板：是否接受在分析前增加一次「确认创作要求」步骤（对现有三步流程有轻微增加）。

P1 · 商品保真 方案 D：C05 参考图角色区分与产品保真

解决：V4.97 把参考图改为纯风格学习（只取色彩），无法保住精确 SKU / 界面 / 结构，软件产出与实体商品容易画错。

建议：区分 product_reference（保真）与 style_reference（学风格）；对必须保真的商品用支持参考编辑的模型或授权素材；缺必要产品资产时返回 needs_input，不生成通用品替代。

改动范围：reference_image.py、media_ad 参考图分支、schemas/前端参考图控件文案、provider 能力声明。

验收：上传商品参考后保留型号/颜色/材质/结构；风格参考不替换产品；软件功能用真实授权产出，不把全息或虚构 UI 当功能。

需拍板：是否引入支持参考图编辑的模型（可能新增供应商与费用），以及授权素材从哪来。

P1 · 质量判定 方案 E：Q01 质检从「有画面」扩展为「有效素材」

解决：image_content_guard 只算 grad/std/uniq，沙发氛围图用于户型软件、用餐图用于返现应用都能通过；异常 fail-open 还复用 has_content。

建议：保留低成本纯色检查；另做产品参与、价值可见、视觉冲突、OCR 检查；检查缺失标 unverified 而非已通过；质量状态独立于文件生成状态，用现有工作区标签展示。

改动范围：image_content_guard、视觉审核链路（可复用 V4.94 的 video_vision_audit 能力）、资产 meta、前端状态标签。

验收：上述两类错配至少进入产品相关性复核；不因漂亮/无字/尺寸正确直接判合格。

需拍板：是否接受每次出片新增视觉模型调用成本；内部 90 分质量门槛是否纳入硬交付条件。

P2 · 稳定性 方案 F：B02 图片任务服务端恢复 + B04 部分成功口径

解决：图片结果只在浏览器 120s 轮询窗口内可见，订阅只回填 video；部分成功被当完整完成，逐尺寸 issues 不展示。

建议：建批次即订阅，图片/视频统一按 asset_id 从批次详情回填；超时只显示「仍处理中/同步失败」不判失败；按 draft_id 恢复服务端草稿；结果区明确「请求 N / 合格 M / 待处理 K」，成功数按可用资产计。

改动范围：CreativeWorkbench 轮询与订阅、api、任务抽屉、creative_tasks 详情聚合。

验收：超过 120s、刷新、短断网后仍能展示结果与具体错误；四个目标出两张显示 2/4 与两个原因，下载只含可用文件。

需拍板：是否接受「草稿按 draft_id 存服务端」带来的会话存储改造。

P2 · 一致性 方案 G：B05 核心 —— 提示词管理真正接线

解决：管理模板（material_prompt_*）与生成模板（media_copy_sys / media_image_sys）是两套 key，intent 与心理层只是展示元数据，保存不影响生成。

建议：明确维护模板与运行模板的单一关联；把已发布版本、intent、所选心理层编译进策划与生成；记录模板 key、版本、正文哈希与最终请求；保留「未接线模板不声称生效」的诚实降级。

改动范围：prompt_catalog、material_prompt_manage、media_ad、routers、前端保存提示。

验收：测试模板加唯一视觉标记后，mock 供应商实际请求能捕获；改心理层使策划相应变化。

需拍板：管理员改一条模板是否应立即影响全平台生成（ blast radius 大，建议先加「发布/回滚」机制）。

P2 · 合规展示 方案 H：B07 规格标准库统一引用

解决：前端 slots 只传 size 与 placement=平台名，缺 spec_id/ad_product/asset_role；后端按展示名精确匹配易失配；结果卡硬编码 JPG/PNG≤30MB。

建议：每个目标传稳定 spec_id，后端解析成冻结版位规则；契约读取真实宽高/格式/容量/安全区；前端读同一快照，未知仍标待核验。

改动范围：schemas 的 slot、前端 slots 构造、media_spec_library、prompt_contract、结果卡展示。

验收：已登记 spec_id 不误降未登记；实际文件规格与导出标签一致，目录与库版本可追溯。

需拍板：spec_id 的生成与维护方式（前端生成还是服务端下发）。

P3 · 业务验证 方案 I：投放对照实验

解决：文档最核心的提醒——生成成功、质量分数、大模型自评分都不能替代真实转化结论。

建议：同产品/目标/受众/版位/落地页条件下比较旧方案与改造方案；先比价值概念，再对胜出概念调开场/视觉；电商看购买 CPA 与 ROAS，订阅看激活/付费/留存退款，线索看合格线索成本与成单；提前定义预算、最小可检测改善、观察窗口。

改动范围：基本不改代码，属运营实验；可能需在导出清单里带 concept_id 以便回流归因。

验收：样本不足不宣称胜出；不以 CTR 变高直接认定有效。

需拍板：由谁在哪个广告账户执行、预算与时间窗口。

六、建议开发顺序与我的取舍

  1. 已完成（V4.102）：7 项确定性缺陷。这些有唯一正确行为、不碰产品语义，先修能让后续方案建立在可信的地基上。
  2. 下一批建议先做 A + H：证据入统一分析、规格统一引用——两者都是「事实层」问题，修复后所有生成任务的可信度整体提升，且不需要你做大的交互取舍。
  3. 再做 B + E：路线独立概念、质检扩展——这是「吸引力/有效性」的核心，但需要先就「是否废弃辅助路线修饰」「是否引入视觉模型成本」拍板。
  4. 然后 C + D + F + G：意图、参考保真、恢复链路、提示词接线——改动面大，建议逐个版本推进，每版独立回归。
  5. 最后 I：投放验证。在代码侧能力齐备后，用少量受控样本验证真实效果，再决定是否扩大自动化交付。
我刻意没有做的：不改三步流程与双工作区布局、不动 V4.101 的创意 brief/框架/换一批、不把「画面不好看」当成提示词问题硬修、不新增进程内任务字典或破坏现有任务单一事实源。这些是我对文档「最小改动」要求的理解。
